# Cross-platform v2 status

The constrained expression host now keeps quoted-literal comparisons safe and allow-lists `Mid`; direct Skia bitmap/PDF entry points reject non-finite dimensions, and empty RDLC font-family values use the deterministic Arial fallback.

For the complete next-session checklist and phase plan, see [`cross-platform-v2-checklist.md`](cross-platform-v2-checklist.md).

The repository now contains the first portable rendering boundary:

- `ReportViewerCore.Rendering.Abstractions` owns backend-neutral geometry, font, text, image resolver, chart, canvas, and document contracts.
- `ReportViewerCore.Rendering.Skia` implements PNG/image, PDF, font metrics, and HarfBuzz text shaping using SkiaSharp and HarfBuzzSharp.
- Font resolution uses the platform font manager by default; callers may register an explicit font file for deterministic shaping, and missing registered files fail before rendering. Matching-RID fallback coverage remains a CI concern.
- `ReportViewerCore.Rendering.Html` emits standalone SVG-backed HTML with escaped text, shared-policy-safe hyperlinks, and embedded PNG images.
- `ReportViewerCore.Rendering.OpenXml` emits valid XLSX and DOCX packages with multi-page text, font family/size/weight/style and color metadata, preserved leading/trailing whitespace, horizontal text/drawing offsets, correctly oriented line shapes, correctly placed external hyperlinks, embedded PNG image parts, native rectangle/line shape parts, and native bar/column/line/area/pie/doughnut chart parts.
- `ReportViewerCore.Engine` now parses tested RDLC multi-tablix, explicit subreport, page header/footer, textbox hyperlinks, nested report items, and styled text, plus mixed textbox/image/rectangle/line/bar/column/line/area/pie/doughnut-chart report-item paths; it keeps non-tablix body items alongside tablixes, applies tablix `SortExpressions` before pagination, traverses nested `TablixMember` group expressions in document order, renders constrained three-or-more-level row-group headers plus group-footer/subtotal templates when matching row templates are present, applies grouped `PageBreak` metadata only when the page-break member's scope prefix changes, evaluates prefix-scoped `CountRows`, `Count`, `First`, `Last`, `Sum`, `Avg`, and `Min`/`Max`, applies allow-listed conditional visibility to standalone items and tablix-cell text/images, preserves the initial `Hidden` state for static `ToggleItem` reports, applies parent offsets including tablix-cell visual items, binds `IEnumerable` rows, maps color/writing mode, applies RDLC parameter defaults including multi-value defaults without overriding caller values, expands allow-listed field/parameter expressions including string concatenation, `IIF`, comparison, `Format`, `IsNothing`, boolean `Not`/`And`/`Or`, and multi-value `Join`, resolves expression-driven and embedded images in body and tablix cells through an injected `IImageResolver`, and splits overflowing rows into `ReportDocument` pages.
- `ReportViewerCore.Headless.LocalReport` exposes the first v2 local workflow; `ServerReport` exposes an explicit `IReportServerTransport` boundary, with `HttpReportServerTransport` providing URL-access rendering and caller-injected authentication.
- `ReportViewerCore.Engine` also exposes `IReportPageSource`/`ReportPageSourceAdapter` as the RPL/SPB migration seam: a legacy pagination adapter can render each page into the same `ReportDocument` consumed by every backend without leaking legacy or System.Drawing types.
- The constrained linear group implementation rejects grouped `PageBreak` locations other than `Between`, while unsupported branching layouts are rejected rather than silently producing incorrect layout.
- Supported sibling branches also accept `PageBreak/BreakLocation=Start`, `End`, and constrained `StartAndEnd` by placing branch groups and supported following static totals at explicit page boundaries; linear groups and other break locations retain their existing constrained behavior.
- The net10 WinForms bridge now snapshots legacy `RPLReport` pages into that seam when the constrained RDLC engine rejects a report. The Windows-only adapter maps page sections, containers/tablixes, text styles and hyperlinks, images, dynamic chart/map streams, lines, rectangles, and page decorations; v2 still owns PDF/HTML/OpenXML/Skia output after the fallback.
- `ReportViewerCore.Headless` selects an injected renderer for a backend-neutral `ReportDocument`; it does not depend on System.Drawing.
- `ReportViewerCore.Rendering.Windows` is a Windows-only WinForms display adapter. It displays pages rendered by the same SkiaSharp backend; it does not introduce a second GDI report renderer. `Microsoft.ReportViewer.WinForms` exposes this as the explicit net10-only `PortableReportViewer` control while retaining the legacy `ReportViewer` control.
- `ReportViewerCore.Sample.CrossPlatform` is a native smoke sample that writes PNG, PDF, HTML, XLSX, DOCX, and RDLC-engine output.
- `ReportViewerCore.Sample.WinForms.V2` demonstrates the Windows adapter with the same `LocalReport`/RDLC workflow.
- `ReportViewerCore.Sample.LegacyBridge` demonstrates the explicit `Microsoft.Reporting.NETCore.LocalReport.RenderPortable` bridge for existing Windows applications and asserts semantic rows plus portable-vs-legacy page count.
- `ReportViewerCore.Sample.WinForms.LegacyBridge` verifies the equivalent `Microsoft.Reporting.WinForms.LocalReport` bridge on Windows, including an explicitly loaded subreport that forces the RPL fallback and checks propagated text/page count.
- `tests/ReportViewerCore.Rendering.Tests` verifies the backend without loading `System.Drawing`, including Thai, Arabic/RTL, CJK and vertical shaping, body/tablix images and image expressions, composite/function/aggregate expressions, sorted/grouped tablixes, charts, links, subreports, multi-tablix layout, and OpenXML package parts.
- The seven v2 libraries have explicit NuGet identities and share the `2.0.0-preview.1` package line. Their package metadata includes the cross-platform migration README, linked checklist, symbol packages, and repository metadata; pack them individually into a release artifact directory and validate the archives before publication. Legacy package identities are intentionally unchanged.

CI runs the portable tests and sample publish for `linux-x64`, `linux-arm64`, `osx-arm64`, `osx-x64`, and `win-x64`. Local release validation has published all five RID payloads, with native execution completed for `osx-arm64`; a separate Windows job builds the WinForms v2 adapter and both legacy bridge samples, then executes the bridge smoke tests against shared golden semantic/page-count expectations. The headless bridge can validate portable semantics on non-Windows hosts, but its legacy page-count comparison is Windows-only because the v1 processor reports no pages off Windows. Native smoke execution runs on matching hosted runners; the `linux-arm64` job validates restore and publish without trying to execute an ARM binary on an x64 runner.

This is an incremental migration. The legacy `Microsoft.ReportViewer.NETCore` and `Microsoft.ReportViewer.WinForms` packages remain compatibility lines and still contain the old GDI/System.Drawing/RPL path, while net10 callers can opt into v2 with `CreatePortableDocument`/`RenderPortable`; the old `Render` path is unchanged. On WinForms, `CreatePortableDocument` first uses the constrained engine and only invokes legacy RPL pagination for unsupported/invalid constrained input. New Windows applications should use the v2 headless API plus `ReportViewerCore.Rendering.Windows`; the WinForms adapter is display-only and receives backend-neutral pages. Subreports use an explicit resolver, support parent-to-child parameter mappings, and have a nesting guard; top-level subreports can be composed alongside tablix/textbox body content, while subreports inside tablix cells or nested containers fail explicitly until the page model supports their placement semantics. The RPL/SPB seam is now an explicit page-source adapter, while constrained grouped tablixes render nested header templates, subtotals, composite group scopes, and basic visual items inside cells. Deeper recursive member features, advanced chart/map contracts, printer output, and golden legacy-vs-v2 comparison remain separate compatibility tasks. Do not load untrusted RDLC sources; arbitrary report code is intentionally not executed by the constrained expression host.

The current NU1903 `System.Security.Cryptography.Xml` advisory is transitive through `System.ServiceModel.Primitives` in the legacy `System.ServiceModel.Http` compatibility/bridge dependency line; the six portable v2 packages do not include that dependency. Resolve the advisory and complete licensing review before calling the preview line stable.

Use the smoke sample from the repository root:

```bash
dotnet run --project ReportViewerCore.Sample.CrossPlatform -- ./artifacts/cross-platform
```

The output directory is intentionally caller-controlled so generated artifacts do not pollute the repository. The sample also writes `rdlc-engine.html` and `rdlc-engine.pdf` from the bundled RDLC/data fixture. HTML, PDF, and OpenXML links allow only relative, `http`, `https`, and `mailto` URLs. OpenXML preserves vertical/RTL text through native styles and maps basic rectangles/lines plus bar/column/line/area/pie/doughnut charts; unsupported chart kinds and full chart/RPL/SPB mapping are later phases.

Run the local equivalent of the portable gate with `dotnet test tests/ReportViewerCore.Rendering.Tests --results-directory ./artifacts/test-results --logger "trx;LogFileName=ReportViewerCore.Rendering.Tests.trx"` and `dotnet publish ReportViewerCore.Sample.CrossPlatform -r osx-arm64 --self-contained false`. The TRX report is written to `./artifacts/test-results/ReportViewerCore.Rendering.Tests.trx`; compiled test binaries remain under `tests/ReportViewerCore.Rendering.Tests/bin/<Configuration>/net10.0/`. Validate the saved test evidence with `python3 .devbuddy/tools/validate_v2_artifacts.py --test-results ./artifacts/test-results/ReportViewerCore.Rendering.Tests.trx` and validate that every RDLC fixture has content and reaches the test output with `python3 .devbuddy/tools/validate_v2_artifacts.py --fixtures ./tests/fixtures/engine --fixture-output ./tests/ReportViewerCore.Rendering.Tests/bin/Debug/net10.0/fixtures/engine`.
For a local v2 package smoke, run `dotnet pack ReportViewerCore.Headless/ReportViewerCore.Headless.csproj -c Release -o ./artifacts/nuget-v2 -m:1 -p:UseSharedCompilation=false` and repeat for the other `ReportViewerCore.*` v2 library projects. The single-node setting avoids MSBuild project-reference contention during pack. Then run `python3 .devbuddy/tools/validate_v2_artifacts.py --packages ./artifacts/nuget-v2 --smoke ./artifacts/cross-platform` to validate archive integrity, metadata, dependency closure, and smoke file signatures.
On Windows, run `dotnet run --project ReportViewerCore.Sample.LegacyBridge -- ./artifacts/windows-legacy-bridge` and `dotnet run --project ReportViewerCore.Sample.WinForms.LegacyBridge -- ./artifacts/windows-winforms-legacy-bridge` to verify both legacy API bridges. The Windows CI job uploads both output directories for post-run semantic inspection.
